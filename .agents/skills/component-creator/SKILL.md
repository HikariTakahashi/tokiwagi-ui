# コンポーネント作成

対象は `HikariTakahashi/tokiwagi-ui`。規則の管理元は [AGENTS.md](../../../AGENTS.md) とし、[issue-to-pr](../issue-to-pr/SKILL.md) の実装フローと併せて使う。

## 名前と対象を決める

- `AGENTS.md` の「コンポーネントの命名規則」を適用する。用途に合わせて `TIcon`、`TButton` などの公開名を決め、実装ファイル・export・登録名・対応するprops型を揃える。
- 依頼されたフレームワークと利用場面を確認する。既存実装と公開入口を調べ、Vue・React・Astroのうち対象となる方式だけを実装する。複数方式を依頼された場合は、同じ用途の公開名と意味を揃え、フレームワーク固有のprops・イベント表現は各方式に合わせる。
- 同じ用途のコンポーネントが既にある場合は重複を作らず、再利用や拡張で依頼を満たせるか確認する。既存APIの改名や互換性変更が必要な場合は、依頼された範囲と利用箇所を確認する。

## 公開APIと振る舞いを実装する

- propsの型・既定値・許可する値・不正値の扱いを定める。必要なイベント・slot・childrenと、classや属性の転送範囲を明確にする。親の責任とコンポーネントの責任を分け、公開APIを利用例で示す。
- 既存の公開入口とディレクトリ構成に合わせて、利用側がインポートできるようにする。アプリ向けの入口からStorybook資料用コードやREADME本文を読み込まない。新しいフレームワークの実装では、依存関係・ビルド・型検査がその方式を扱えることを確認する。
- 色は `tokens/` の既存トークンを参照する。コンポーネント内に色値を複製しない。状態に応じた背景と前景の組み合わせは、Storybookのカラー使用ルールに従う。
- アイコンを使う場合は公開済みコンポーネントを再利用する。アイコンコンポーネント自体を作る場合は `icons/` のSVG原本と既存の表示変換を使い、`AGENTS.md` のアイコン資産の規則に従う。
- 操作要素の読み上げ名、キーボード操作、フォーカス、無効状態を設計する。装飾アイコンは重複読み上げを避け、アイコンだけの操作には親のbutton/linkに目的が分かる名前を付ける。状態を色だけで伝えない。
- 描画IDを使う場合は複数インスタンスで衝突しないようにする。SSRを対象とする方式では、サーバー描画とクライアントのハイドレーションでIDが一致する方式を使う。

## 利用例と検証を整える

- Storybook説明ページを作る場合は、[ドキュメントUIルール](../../../src/stories/component-documentation-rules.mdx)を読み、[共通部品](../../../src/stories/components/ComponentDocumentation.tsx)と共通CSSを再利用する。ページ構成・操作UI・コード欄・API表を独自に再定義せず、固有の設定・比較・使用例だけを追加する。寸法・配色の管理元はルール原本と共通CSSとする。
- 対象フレームワークだけをReact・Vue・Astroの順に表示し、初期設定を実コンポーネントの既定値に合わせる。必須propsには用途を説明できる代表値を選ぶ。方式の切り替えで設定を保持し、見本とコピー可能な使用コードを一致させる。比較見本は初期状態で折りたたむ。
- Storybookまたは対象方式の確認ページで実コンポーネントを動かし、基本状態とAPIに応じた状態・サイズ・トークン色を比較できるようにする。公開入口からのインポート方法と、読み上げ名など利用側が担う点を文書化する。
- Storybookでは390px・1440pxで表示と局所スクロールを確認する。設定保持、見本とコードの一致、コードのコピー成功・失敗・通知リセット、比較見本の開閉を検証する。非同期読み込みがある場合は読み込み中・失敗・再試行を確認し、VueのアンマウントやAstroのID分離など既存の描画条件を維持する。Storybook専用コードをアプリ向けの公開入口へ含めない。
- `AGENTS.md` の必要な検証を実施する。意味のある境界条件（不正なprops、複数インスタンス、状態やイベントなど）を対象に必要なテストを追加する。テストの名前と目的・条件・期待結果のコメントは日本語で書く。
- UI変更時の型検査・両ビルドと、モバイル／デスクトップ表示、キーボードフォーカス、操作要素のホバー・押下を確認する。対象方式でSSRを使う場合は、サーバー描画とハイドレーションも確認する。
- 変更内容、公開API、利用方法、検証結果と残る制約をまとめ、コミット・PRは `issue-to-pr` の手順に従う。
