# GitHub プルリクエストの作成

`HikariTakahashi/tokiwagi-ui` の実装がプルリクエストを作成できる状態になったときに、このスキルを使う。

1. リポジトリ、`gh auth status`、ブランチ、作業ツリー、差分を確認する。関係のない変更をコミットやプルリクエストに含めない。作業用ブランチを使い、実装を `main` に直接プッシュしない。
2. 今回の作業を管理する Issue の URL・状態・完了条件と、最終差分を照合する。対象の Open Issue が未作成・未確定の場合は、その状態と理由を報告して PR 作成を止める。完了済み Issue や背景・参考への参照だけで代替しない。作業中に Issue が閉じられたり変更範囲が広がったりした場合は、[issue-to-pr の手順1](../issue-to-pr/SKILL.md)に戻って対象を見直す。投稿拒否の場合も過去 Issue に付け替えて続行しない。
3. `README.md` に記載された関連するチェックを実行し、結果を確認する。`.github/PULL_REQUEST_TEMPLATE.md` に沿って、対象 Issue、対応した完了条件、残作業、背景・参考、変更内容、検証結果、人によるレビューで確認してほしい点をまとめる。対象 Issue の完了条件をすべて満たす場合に限り `Closes #N` を使う。一部対応の場合は `Refs #N` を使い、残作業を具体的に記す。複数の対象 Issue があれば、それぞれについて対応内容と完了・一部対応を区別する。過去 Issue・PR は「背景・参考」欄へ分け、対象 Issue の代わりにしない。
   UI変更を含む場合は [github-media-attach](../github-media-attach/SKILL.md) を使い、Computer Useで確認・撮影したスクリーンショットを「添付ファイル」欄に埋め込む。操作の流れを示す必要がある場合は動画も使う。撮影・添付できない場合は、その理由と未完了の項目を記載する。
4. [issue-to-pr の手順5](../issue-to-pr/SKILL.md)に従って承認された変更をコミットしてプッシュする。PR 作成の直前に手順2の照合を再度行い、`gh pr create --repo HikariTakahashi/tokiwagi-ui --base main --body-file ...` でプルリクエストを作成する。本文には一時的な UTF-8 ファイルを使う。人によるコメントや修正を受けられるよう、作成時にマージしない。
5. プルリクエストの URL、対象 Issue、対応した完了条件と残作業、実施したチェック、人による確認が必要な点を報告する。作成者が `HikariTakahashi` の場合、同じアカウントを正式なレビュアーとして指定しない。GitHub は自己承認を承認として扱わない。
