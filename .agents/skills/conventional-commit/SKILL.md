# コミット作成

コミット名は [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) に従い、次の形式で指定する。

```text
<type>[optional scope][!]: <description>
```

- 新機能は `feat`、バグ修正は `fix` を使う。その他の変更には内容に合う `docs`、`refactor`、`test`、`chore` などを使える。
- `scope` は必要なときだけ、変更箇所を表す名詞として括弧内に置く。
- `description` は実際の変更を短く具体的に表す。例: `fix(calendar): イベントの重複送信を防ぐ`。
- 破壊的変更は型または scope の直後に `!` を付けるか、本文の後に `BREAKING CHANGE: <内容>` フッターを付ける。必要な背景や Issue 参照は、空行を挟んだ本文・フッターに記載できる。

## コミットの分割方針

- 差分を単一コミットにまとめることを前提にしない。変更の目的や責務が異なり、分けることでレビュー・履歴の理解・変更の取り消しがしやすくなる場合は、複数コミットに分ける。
- ファイル数や行数だけで分割しない。依存関係の追加、機能の実装、テスト、利用例、文書などを判断の起点とし、密接に関連する変更は同じコミットに含める。各コミットが意味のある変更として成立し、必要な型検査・テスト・ビルドを通せる単位にする。
- コミット間に依存関係がある場合は、依存される変更から順番に並べる。同じファイルに複数の目的の差分がある場合は、差分単位でステージする。分割のために既存の作業ツリーの変更を失わない。

## 実行手順

1. 作業ツリーの差分とステージ済み変更を確認し、今回の対象差分を特定する。他者の変更や無関係なファイルを含めない。上記の方針に沿って、単一または複数のコミット構成を決める。
2. 検証結果を確認し、**各コミットの対象ファイル・差分の要点・具体的なコミット名・実行順序**をまとめてユーザーに提示して、コミット実行の明示的な許可を求める。ユーザーが分割案全体を承認した場合は、その案に含まれる各コミットについて許可を取り直す必要はない。ユーザーが別の分割や名前を指定したら、形式と変更内容に合う範囲でそれを優先する。
3. 許可後に、合意した順序で各コミットの対象差分だけをステージし、ステージ済み差分を確認してから、合意した名前でコミットする。許可後に対象や内容、分割構成が実質的に変わった場合は、変更後の内容を示して再度許可を得る。
4. 作成した各コミットのハッシュ、名前、含めた変更、検証結果を報告する。途中でコミットが失敗した場合は、作成済みのコミットと未コミットの差分を報告して原因を伝え、勝手に別の内容で再試行しない。

ユーザーの許可前に `git commit` を実行しない。
