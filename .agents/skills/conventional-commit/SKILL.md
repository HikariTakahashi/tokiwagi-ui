# コミット作成

コミット名は [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) に従い、次の形式で指定する。

```text
<type>[optional scope][!]: <description>
```

- 新機能は `feat`、バグ修正は `fix` を使う。その他の変更には内容に合う `docs`、`refactor`、`test`、`chore` などを使える。
- `scope` は必要なときだけ、変更箇所を表す名詞として括弧内に置く。
- `description` は実際の変更を短く具体的に表す。例: `fix(calendar): イベントの重複送信を防ぐ`。
- 破壊的変更は型または scope の直後に `!` を付けるか、本文の後に `BREAKING CHANGE: <内容>` フッターを付ける。必要な背景や Issue 参照は、空行を挟んだ本文・フッターに記載できる。

## コミットの分割方針

**目的ごとに分割することを原則とし、独立してレビュー・取り消しができる変更が複数あれば、複数コミットにする。** ユーザーが単一コミットを明示した場合はその指定を優先する。

- まず差分から変更目的を列挙し、目的ごとにコミット候補を作る。同じ依頼・Issue・機能に属すること、同じtype・scope・ファイルであることだけを、まとめる理由にしない。小さな差分でも目的が独立していれば分ける。
- 分割候補として、動作を変えない事前整理・共通処理の抽出、個別の機能追加や不具合修正、既存機能のテスト補強、利用例・文書の整備、開発環境・CI・依存関係の更新を確認する。すべての分類を作る必要はないが、見つかった独立した目的を一つのコミットに押し込まない。
- **依存関係があることと、一つにまとめる必要があることを区別する。** 先行コミットを適用した状態で後続コミットが成立すれば、順番を付けて分けられる。事前整理→機能実装→独立した文書整備など、依存される変更から並べる。
- 同じコミットに含めるのは、一つの目的を成立させるために一緒に必要な差分。例として、バグ修正とその回帰テスト、機能とその検証に必要なテスト、依存パッケージの更新と対応するロックファイル、公開API変更と利用側の必須修正はまとめる。機能実装とテストを機械的に分離しない。
- 各コミットは、それまでのコミットを適用した状態で意味のある変更として成立し、必要な型検査・テスト・ビルドを通せる単位にする。後続コミットがないと壊れる分け方は避け、境界や順序を調整する。依存が強く分割できない場合は、その具体的な理由を示す。
- ファイル数や行数、目標のコミット数だけで分割しない。棚卸しの結果、目的が一つで独立した変更がなければ単一コミットでよい。その場合も、分割を検討したうえで単一とした理由を提案に添える。「関連する変更だから」「同じIssueだから」だけでは理由にならない。

### 分割の判断例

| 差分 | コミット構成 |
| --- | --- |
| 共通処理の抽出と、その処理を使う新機能 | 動作を変えない `refactor` → 新機能と必要なテストの `feat` |
| 同じファイルにある、原因が異なる2件の不具合修正 | 修正と対応する回帰テストを一組にした2つの `fix`。ファイル内の差分も分けてステージする |
| 新機能、独立した使い方ガイド、CIの高速化 | 機能と必要なテストの `feat`、ガイドの `docs`、CIの変更の `chore` |
| 1件の不具合修正と、その回帰テストのみ | 一つの `fix`。テストはその修正の正しさを示すため一緒に含める |

## 実行手順

1. `git status --short`、`git diff`、`git diff --cached` と未追跡ファイルの内容を確認し、今回の対象差分を特定する。他者の変更や無関係なファイルを含めない。
2. **ステージする前にコミット構成を作る。** 変更目的ごとに対象ファイル・差分を割り当て、各候補が独立してレビュー・取り消しできるかを確認する。独立した候補は分け、依存順に並べる。同じファイルに複数の目的があれば、ファイル名だけでなく対象のhunk・変更箇所も特定する。単一案になった場合は、事前整理・個別の修正・文書・設定などを分けられないか再確認する。
3. 検証結果を確認し、**各コミットの対象ファイル・差分の要点・具体的なコミット名・実行順序と依存関係**を番号付きでまとめてユーザーに提示して、コミット実行の明示的な許可を求める。単一の場合はその理由も示す。ユーザーが分割案全体を承認した場合は、その案に含まれる各コミットについて許可を取り直す必要はない。ユーザーが別の分割や名前を指定したら、形式と変更内容に合う範囲でそれを優先する。
4. 許可後に、合意した順序で**一つのコミットの対象差分だけ**をステージする。ファイル単位ならパスを指定した `git add`、同じファイルの一部なら `git add -p` または対象hunkを限定したパッチを使う。複数候補をまとめてステージする `git add .` や `git add -A` は使わない。既存のステージ済み変更が混在している場合は、所有者と対象を確認し、無断で解除・取り込みをしない。分割のために作業ツリーの変更を失わない。
5. 各コミットの直前に `git diff --cached --stat`、`git diff --cached`、`git diff --cached --check` で、予定した目的の差分だけが含まれることを確認する。検証は可能な範囲でそのコミットまでの状態に対して行い、後続の未コミット変更を含む作業ツリーでの成功を、各コミット単体の検証済みとは扱わない。合意した名前でコミットし、残りの差分を確認して次の候補へ進む。許可後に対象や内容、分割構成が実質的に変わった場合は、変更後の内容を示して再度許可を得る。
6. 作成した各コミットのハッシュ、名前、含めた変更、検証結果と未検証の範囲を報告する。途中でコミットが失敗した場合は、作成済みのコミットと未コミットの差分を報告して原因を伝え、勝手に別の内容で再試行しない。

ユーザーの許可前に `git commit` を実行しない。
